02 / Design decisions

技術の数ではなく、
責務の分け方がポイント

面接で軸にする4つの設計判断です。以降で実装と制約を図解します。

Type safety

共有Zod schemaをAPI契約にする

主なBBS API / BFFで同じ検証規則を使い、HTTP境界の不正データを実行時にも検出します。

Consistency

Operations

User experience

Bottom Navigation、pending、skeleton、optimistic updateを役割別に実装します。

Build-time static asset guard

  • Live data: Thread / Search / Profileはno-store
  • Tag一覧: force-cache + 300秒revalidation
  • Static asset / R2画像: 1年immutable
  • 静的asset検証script

08 / Interview

面接で伝える4本柱

スライドには一言、口頭では設計範囲とtrade-offまで説明します。

共有SchemaでAPI境界を型安全に

主なBBS APIでZodをValidation・OpenAPI・TypeScript型・Response検証へ再利用。

Hono RPCやDB schema自動生成ではない点も説明し、型安全性の実際の範囲を明確にします。

WebSocketは通知、HTTPは正本

Thread単位のDOが新規Postを通知し、SWRでD1から再取得。

即時性を得つつ、WebSocketとDBの二重状態管理を避けた責務分離を説明します。

Cache障害をBuild guardへ

immutable cacheを維持し、直前snapshotの欠落assetを検査・復旧。

iOS上の旧CSS、woff2 404、Workers CPU超過から再発防止へつなげた過程を説明します。

Mobileで反応が返るUX

Tap・待機・遷移・失敗の各状態へfeedbackを対応。

見た目ではなく、操作認知と不安低減を目的として、rollbackやreduced motionまで説明します。

聞かれやすい質問

なぜ通常APIだけでなくWebSocketを使ったのですか？

他Userの新規投稿をpollingなしで通知するためです。投稿データ自体はSocketへ載せず、通知後に通常APIでD1の正本を取り直します。

Durable Objectsは何を保存していますか？

ApplicationのThreadRoomは永続データを保存しません。thread:{threadId}単位で接続中socketをまとめ、post.createdをfan-outします。

FrontendからDBまで完全に型安全ですか？

いいえ。主なBBS API / BFFでは共有Zod schemaで境界を検証し、DrizzleはDB queryを型推論しますが、DBからZodの自動生成やHono RPC clientは使っていません。

Cloudflareを選んだ理由は費用ですか？

コードから確認できるのは、Workers、D1、R2、DOへ基盤を集約し、常時起動VMや外部RDB設定を持たないことです。本人の選定理由と実料金は未確認なので断定しません。

WebSocket切断中のeventはどうなりますか？

指数backoffで再接続しますが、event履歴、replay、再接続直後の明示的な全件refetchはありません。現行の保証は接続中の変更通知です。

自動テストはありますか？

現状、test runnerとtest suiteは確認できず、.github/workflowsも存在しません。確認済みの自動検証はTypeScript typecheck、Next build、Biome、pre-commitのlint-stagedです。
